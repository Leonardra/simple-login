# simple-login

An MVVM login screen for iOS built with SwiftUI and the Observation framework:
protocol-based authentication, Keychain-backed sessions, inline validation and a
test suite that runs without a network or a server — plus one opt-in suite that
verifies the deployed API's contract for real.

- **Language / UI:** Swift, SwiftUI (`@Observable`, no `ObservableObject`/Combine)
- **Minimum OS:** iOS 17.0
- **Toolchain:** Xcode 16+ (project is object version 110, generated by Xcode 27)
- **Dependencies:** none — only `Foundation`, `SwiftUI`, `Security` and `Testing`

## Running it

```sh
open simple-login.xcodeproj          # then ⌘R
```

The app launches straight into the **live Ajo API**
(`https://nutmtrainingbackend.dataalcomms.com/v1`), so sign in with the account the
backend documents for demos:

| Field    | Value                        |
| -------- | ---------------------------- |
| Email    | `adaeze.okonkwo@nutm.edu.ng` |
| Password | `password`                   |

Any other combination is rejected by the server and shown with the server's own
sentence (e.g. *"That email and password don't match."*).

To work offline — on a plane, or where the venue wifi is a liability — run against
the in-memory mock instead. Set `USE_MOCK_AUTH=1` in the scheme's run environment
(*Product ▸ Scheme ▸ Edit Scheme ▸ Run ▸ Arguments*). The mock accepts the same demo
credentials, so switching modes does not change what you type, and it fails with the
same message after a deliberate 1.5 s delay so the loading state stays visible.

### Tests

```sh
xcodebuild test -project simple-login.xcodeproj -scheme simple-login \
  -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:simple-loginTests
```

Or just press ⌘U in Xcode.

The default run needs **no network and no server**: every `APIAuthService` test drives a
stubbed `URLProtocol` with responses captured verbatim from the live endpoint. One
suite is different — it talks to the deployed API for real, and is skipped unless you
opt in, so a CI box or a server outage can never turn it into a red build:

```sh
TEST_RUNNER_LIVE_AUTH_TESTS=1 xcodebuild test -project simple-login.xcodeproj \
  -scheme simple-login -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:simple-loginTests/LiveAuthIntegrationTests
```

## Architecture

```
Views/                      SwiftUI only — no business logic
  RootView                  switches Login / Home on `isAuthenticated`
  LoginView                 the form, focus, show/hide password, inline errors
  HomeView                  post-login placeholder, greets by name, Log Out
  Components/ErrorBanner    dismissible failure banner
ViewModels/
  LoginViewModel            @MainActor @Observable — all state and decisions
Services/
  AuthServiceProtocol       the one thing the view model needs
  APIAuthService            real URLSession implementation
  MockAuthService           offline implementation for the demo and previews
  AuthTokenStore            persistence boundary + Keychain and in-memory stores
Models/
  AuthToken                 the session, and the endpoint's JSON contract
  AuthUser                  the profile delivered with the session
  APIError                  the `{code, message, details?}` error envelope
  AuthError                 the closed set of user-facing failures
Utilities/
  LoginValidator            pure validation rules
  KeychainHelper            Security-framework wrapper
  AppConfiguration          base URL and which service to run against
```

Data flows one way: a view calls a view-model intent, the view model talks to the
two protocols, the resulting state change re-renders the view. Views never touch
`AuthServiceProtocol`, `AuthTokenStore` or the keychain directly.

### Where the comments are

The sources carry **no comments at all** — every explanation, `WHY:` note, file
header and `// MARK:` marker was extracted verbatim into
[`CODE_COMMENTS.md`](CODE_COMMENTS.md). Each entry is anchored to the line number
it occupied *before* extraction, so it still points at the right place in the code.

### Why the seams are where they are

- **`AuthServiceProtocol`** — the view model is tested against `MockAuthService`
  and hand-written stubs instead of a stubbed `URLProtocol`, so the test suite
  never opens a socket.
- **`AuthTokenStore`** — the view model reads the token synchronously in `init`,
  so the first frame already knows whether to show Login or Home. There is no
  "logged out" flash and no second loading state. A protocol is what lets tests
  use an in-memory store rather than the simulator's shared keychain.
- **`AuthError.from(_:)`** is the only path from a thrown error to user-visible
  text. A raw `localizedDescription` ("The operation couldn't be completed. Error
  Domain=NSURLErrorDomain Code=-1009") is never shown.
- **`LoginValidator`** holds the rules as pure functions so the view, the view
  model and the tests all read the same source of truth.
## Behaviour worth knowing

- **Sessions survive relaunch.** The token is written to the Keychain under a
  namespaced service string with `kSecAttrAccessibleAfterFirstUnlock`. Log out
  deletes it. Only the access token is persisted — never the password.
- **Log out is local-first.** The session is cleared from memory and the Keychain
  *before* the revoking `DELETE` is attempted, and the call is best-effort: a user
  on a plane must not be stuck staring at a signed-in screen. A token that outlives
  log out server-side is the smaller problem, and it expires on its own.
- **The password is cleared after a failed attempt**, so a stale credential does
  not sit in memory in front of the next person holding the phone. The exception is
  a `422` that blames the password — the user cannot act on "is required" if the
  field they must fix was emptied.
- **The server's verdict outranks the local rule.** A `422`'s per-field issues are
  shown under the fields they name and are dropped as soon as the user edits that
  field, because the sentence described the value the server rejected.
- **The Log In button is disabled until the form is valid**, and the view model
  independently ignores a second submission while one is in flight (a double tap
  can deliver both taps before SwiftUI re-renders the disabled state).
- **Validation messages appear only after a field has been edited**, so a fresh
  screen does not open covered in red text.
- **Keyboard:** Next moves from email to password, Go submits. The show/hide
  toggle re-applies focus explicitly, because swapping `SecureField` for
  `TextField` destroys the field and would otherwise dismiss the keyboard.
- **Accessibility:** every control has a label and hint, error messages are
  announced, the decorative iconography is hidden, and the layout is checked at
  accessibility text sizes in the previews.

## The backend contract

The app talks to the Ajo API (NUTSOE 806). Its Swagger UI is at
`https://nutmtrainingbackend.dataalcomms.com/swagger`. Two endpoints are used:

| Method   | Path             | Purpose                              |
| -------- | ---------------- | ------------------------------------ |
| `POST`   | `/v1/auth/login` | exchange credentials for a session   |
| `DELETE` | `/v1/auth/session` | revoke the session (used on log out) |

`/v1/auth/login` takes `{"email": …, "password": …}` and answers `200` with:

```json
{
  "token": "ajo_sess_25f7ffbb8a4255cbf69ef266f0ee6e03",
  "expiresAt": "2026-10-30T21:59:06Z",
  "user": {
    "id": "3b241101-e2bb-4255-8caf-4136c566a962",
    "displayName": "Adaeze Okonkwo",
    "email": "adaeze.okonkwo@nutm.edu.ng",
    "avatarUrl": null,
    "createdAt": "2026-08-13T04:37:46Z"
  },
  "refreshToken": "ajo_refr_4aaa93308073977788240d6d657e1b35",
  "refreshExpiresAt": "2026-11-22T21:59:06Z"
}
```

`AuthToken.init(from:)` also accepts the legacy `access_token` / `expires_at` /
`expires_in` spellings, so a server rollback would not break the build — but the
camelCase shape above is what the endpoint sends today.

### Errors

Every non-2xx `/v1` response uses one envelope, and the client renders the server's
`message` **verbatim** rather than inventing its own copy:

```json
{ "code": "unauthorized", "message": "That email and password don’t match." }
```

| Status            | `code`                | `AuthError`                            | What the user sees |
| ----------------- | --------------------- | -------------------------------------- | ------------------ |
| `401`, `403`      | `unauthorized`        | `.invalidCredentials(message:)`        | the server's sentence |
| `422`             | `validation_failed`   | `.validation(fieldIssues:)`            | each `details[].issue` under its own field |
| `429`             | `rate_limited`        | `.rateLimited(retryAfter:)`            | how long to wait, from `Retry-After` |
| `5xx`             | —                     | `.serverError(statusCode:)`            | "the server is having trouble" |
| anything else     | —                     | `.serverError(statusCode:)`            | a generic retry message |
| no response       | —                     | `.networkUnavailable` / `.unknown`     | an offline message |

A `422` is the one case that is *not* a banner: `details` names fields, so each issue is
shown under the field it belongs to. Only if no issue can be attributed to a field this
screen renders does the generic sentence fall back to the banner — and an unrecognised
`code` deliberately does **not** surface the server's wording, because a joke or internal
message would read as a bug.

### Pointing it somewhere else

Set `AUTH_BASE_URL` in the scheme's run environment; no code change is needed:

```
AUTH_BASE_URL = https://api.your-host.com/v1
USE_MOCK_AUTH = 0
```

`AppConfiguration` reads those variables, and the `/v1` suffix belongs to the base URL
because `APIAuthService` appends only the resource path.

The one place the contract is pinned in code is `AuthToken` — it owns both the JSON
mapping and the `JSONDecoder` it must be read with, so the service itself only has to
translate transport concerns into `AuthError`. Dates are decoded with `.iso8601`: on the
default `.deferredToDate` strategy a numeric `expiresAt` is silently read as seconds
since 2001, which would decode "successfully" with an expiry years off. A bare number is
rejected loudly instead.

## Tests

69 tests across 9 suites. The eight offline suites need no network and no server; the
ninth is the opt-in live run described above.

| Suite | Covers |
| ----- | ------ |
| `LoginViewModel` | button enablement, whitespace-normalized email, success persisting the token, greeting by name |
| `LoginViewModel failures and session lifetime` | error copy, password cleared on failure, loading on/off, double submit, session restore, log out (local-first, server-revoked), server-side `422` routing |
| `APIAuthService` | request shape, the 200 contract, and every error mapping — against responses captured verbatim from the live endpoint |
| `AuthError mapping` | the `{code, message, details}` envelope, per-field issues, status-code fallbacks, user-facing copy |
| `Token and store behaviour` | the JSON contract (current and legacy), expiry handling, the in-memory store |
| `AppConfiguration` | the base URL parses, the resource paths match the contract, production ships the real client |
| `LoginValidator` | parameterized accepted/rejected email shapes, password boundary, message copy |
| `KeychainHelper` | a real Keychain round trip under a test-only service namespace |
| `Live endpoint integration` | *(opt-in)* a real login, a real rejection, and a keychain round trip against the deployed API |

Async tests use `SuspendedAuthService`, which holds a login call open until the
test releases it, so "the spinner is visible while the request is in flight" is
asserted at a deterministic point instead of by racing a timer. `SpyAuthService`
counts the calls it receives, so a server-side test that forgets to fill the form
cannot pass by asserting against local validation messages instead.

## Known limitations

- `HomeView` is a placeholder; there is no authenticated feature set behind it.
- The session's profile is **not** restored on relaunch — only the token is
  persisted, so Home greets a returning user without a name. The profile arrives
  with the login response and is held in memory; re-reading it from `GET /v1/me` is
  the follow-up.
- `refreshToken` / `refreshExpiresAt` are decoded but unused: no endpoint here needs
  a refresh round trip. The same goes for `AuthToken.isExpired`, which is implemented
  and unit-tested, ready for a refresh interceptor.
- "Forgot password?" is a stub alert.
- Validation is intentionally pragmatic (not RFC 5322) and is a UX affordance
  only — the server remains the authority on credentials.
